# Groups

Groups, memberships, and roles move out of FusionAuth Entities into a Cloudflare D1 SQL database. FusionAuth remains the system of record for **user identity** only.

Groups that are reverse-DNS names implicitly contain all subgroups under that group. For example, if `org.example` is a group, then it also contains `org.example.subgroup`. However, if `org.example.subgroup` is a group, then it does not contain `org.example`.

Group pages are accessible to anyone. Non-members can view the group description, artifacts, members, and counts. They can't modify anything though.

## Creating a new group

When a user wants to create a new group, they take these steps:

1. Create a new account if they haven't already signed up. This is done using FusionAuth via OIDC. When the browser returns from OIDC after a successful sign-up, the tokens will represent a user in FusionAuth.
2. Click the "New Group" button.
3. Type in the name of the group (i.e. `org.example`).
4. Click "Create Group".

After these steps are complete, the Group object is created in the database in the `groups` table and has this state (some columns omitted for brevity):

| name        | state   | verification_code |
|-------------|---------|-------------------|
| org.example | PENDING | 1234567890abcdefg |

If the user uses a short-name rather than a reverse-DNS name, the state will be (some columns omitted for brevity):

| name          | state    | verification_code |
|---------------|----------|-------------------|
| my_short_name | VERIFIED | NULL              |

The validation for the group consists of these checks:

* No group with this name already exists after lowercasing it.
* The group name is either a short-name or a reverse-DNS name (i.e. `org.example` is allowed but `example.org` is not).
* The group name is a valid java package name.
* The group name is no longer than 255 characters.
* There is no group whose name is a prefix of this group name using dot boundaries. For example, if `org.example` is an existing group, a new group named `org.example.subgroup` cannot be created separately. That group falls under `org.example` group. The reverse is allowed. But following the dot boundary rule, an existing group named `org.examples` would not prevent the group `org.example` from being created. Nor would an existing group named `org.examples.subgroup` prevent `org.example` from being created. (HINT: query using a `LIKE`, split the group names on `.`, and compare segments)

The method of handling reverse-DNS validation is using a list of TLDs that are able to be registered and used for websites. This list is maintained by the IANA and is available at https://data.iana.org/TLD/tlds-alpha-by-domain.txt. The application will download this at startup and cache it in memory. Only a restart will reload this file. The first part of the group name must be a TLD if the group name contains a period.

All group names are normalized to lowercase before validation, and that is what is stored in the database.

Verification codes are generated at random, stored in the database during creation, and immutable. If the verification code is NULL, that means the group does not ened to be verified. This usually indicates a reserved or pre-created group.

### Reverse-DNS group verification

If the group is a reverse-DNS group not in the `github.io` domain, it will require DNS verification. This means there will be a record in the `group_verifications` table that looks like this (some columns omitted for brevity):

| group_name  | started_at           | last_checked_at      |
|-------------|----------------------|----------------------|
| org.example | 2021-01-01T00:00:00Z | 2021-01-01T00:00:00Z |

There will be a background task that checks the `group_verifications` table every 3 minutes and does a DNS lookup to see if the `verification_code` on the `group` table matches the TXT record for the domain. The domain is calculated by reversing the group name to produce a valid DNS name. For example, the group `org.example` is converted to `example.org`. This domain is used to retrieve the TXT record from the DNS server. This task will run in every JVM that is running the application. Duplicate checks and race conditions are not a concern. If the JVM dies or sleeps, that's fine because when it is running, the checks will occur. The check is based on the number of milliseconds from the `last_checked_at` instant. And the scheduled task runs when the application is started and then every 3 minutes. Therefore, it is guaranteed to run while a user is waiting for DNS verification because they will be actively using the application. 

DNS errors are silently ignored since they will be tried again later.

Once the TXT record is found, the `state` will be updated to `VERIFIED` on the `groups` table and the row in `group_verifications` will be deleted.

If after 48 hours after `started_at` the TXT record is not found, the `state` will be updated to `FAILED` on the `groups` table and the row in `group_verifications` will be deleted. Once a group has failed verification, the user must click on a button on the Group page that says "Re-try verification". This updates the row in the `groups` table to have a state of `PENDING`. It also creates a new row in the `group_verifications` table.

Once a group is verified, the `verified_at` column will be updated to the current time.

*NOTE:* The reason the `verification_code` is stored in the `groups` table is so that it can be reused across verification processes or used for verification periodically in the future after the first verification is performed.

### GitHub group verification

If the group is a reverse-DNS but in the `github.io` domain (i.e. `io.github.example`), the group will be verified using OAuth when the user clicks the "Verify using GitHub" button on the Group page. Since the GitHub API requires an OAuth token with the `read:org` scope, the Kickstart needs to be udpated to include an identity provider for GitHub with that scope (and any other scopes that are required - you should read the GitHub docs to figure out what scopes are required).

If the User signed up with GitHub, their GitHub account will be linked to their FusionAuth account. The application can query FusionAuth to determine if there is an IDP link to GitHub. If there is, it should use the GitHub tokens stored on the link in FusionAuth to call the GitHub API and determine if the user is a member of the GitHub organization using the `/orgs/{org}/members/{username}` API, or if this group is the user's personal GitHub account.

If these tokens cannot be used to call the GitHub API due to a `401` status code, then the Unlink API in FusionAuth should be called. This will remove the link. Then the process to link their GitHub account to FusionAuth below should be followed instead. 

If the user does not have a GitHub link, they will use FusionAuth via an `idp_hint` to connect their GitHub account. This leverages the standard OIDC workflow, but triggers FusionAuth to directly federate to GitHub. Once they return to the application and the IDP link exists in FusionAuth, the instructions above will be followed to verify they are part of the GitHub organization, or if the group is their personal GitHub account.

If the user is part of the GitHub organization, or the group is their personal GitHub account, the group's state will be set to `VERIFIED`. If they are not, the Group's state will remain `PENDING`.

This verification process does not require a row in the `group_verifications` table. Rather, when a user is viewing the Group page, they will see a message that says "This group is not yet verified. Please connect a GitHub account that has access to the <name> organization to verify."

Once a group is verified, the `verified_at` column will be updated to the current time.

*NOTE*: GitHub groups are not verified by default, and they never time out and move to the `FAILED` state.

*NOTE*: Future verification of GitHub groups is out of scope for this design.

## Deleting a group

If a group has no published artifacts, it can be deleted. The S3 API is used to query the R2 bucket to determine if the group has any published artifacts (i.e. `org.example` should not exist in the R2 bucket).

The group can only be deleted by an `OWNER` of the group.

When an existing `OWNER` of a group wants to delete the group, they take these steps:

1. Go to the group page.
2. Go to the "Settings" tab.
3. Click the "Delete Group" button in the "Danger Zone".
4. Click "Confirm" in the pop-up modal dialog.

Once these steps are complete, the group is deleted from the database only.

*NOTE*: There is a race condition since someone could publish an artifact to the group before the group is deleted. Since we are not deleting the artifacts, this race condition is not a concern. If someone creates the group again in the future, the existing artifacts will show up under the group.

## Group visibility

Any user that is a member of a group can view the group page, including all `ACTIVE` and `PENDING` members.

## Group membership

Users that belong to a group are called members.

### Inviting a user to a group

When an existing member that has the `OWNER` role in the group wants to invite another member to one of their groups, they take these steps:

1. Go to the group page.
2. Click the "Invite Member" button.
3. Type in the email address of the user to invite and select their role.
4. Click "Invite".

First, the email is lowercased and trimmed. After the email is normalized, validation for this form includes:

* Ensure the email is valid.
* Ensure the user is not already a member of the group.
* Ensure the user is not already invited to the group.

When they complete these steps, the application will execute code to complete these steps:

1. Call the FusionAuth User API to determine if the user exists.
2. If the user exists, ensure the user has a registration for this application by checking the user's registrations in the response. If they don't have a registration, call the registration API to create a registration for them. Then call the FusionAuth email API to send the user an email telling them they have been invited to the group. This will use a specific email template in FusionAuth for invitations only. This email needs to be added to Kickstart and the code will reference it by ID.
3. If the user doesn't exist, call the FusionAuth Registration API to create a new user and register them for the application in one step. This API call will include the `sendSetPasswordIdentityType` parameter set to `email`. Kickstart needs to be updated with a new email template that includes information about how the user has been invited to the group and they need to click the link to set up their account to view the invitation. The Kickstart also needs to be udpated so this template is connected to the application for use as the `Set up password` email template. This also requires that the Tenant is configured with an SMTP server. So the Kickstart needs to be updated to set Sendgrid as the SMTP server for the application. The password should be an environment variable passed into the Kickstart.
4. Add a new row to the `members` table with the `group_name` and the user `id` that was returned from either of the FusionAuth User APIs called above.

Once the code has completed, there will be a new row in the `members` table with this state (some columns omitted for brevity):

| group_name  | user_id                              | invited_by                           | role  | state   |
|-------------|--------------------------------------|--------------------------------------|-------|---------|
| org.example | 252f8953-e2fb-42a2-a7bf-0919df5e1340 | 5695325a-7e58-44a9-982c-34bcf40fdead | OWNER | PENDING |

#### Accepting an invitation

When a user has a `PENDING` invitation to a group, they can accept the invitation by following these steps:

1. Go to the group page, which they will see in their UI since they have a pending invitation.
2. On the Overview, there will be a box that says, "Accept invitation?" with two buttons "Accept" and "Decline".
3. Click the "Accept" button.

After the user has accepted the invitation, they are shown the group page as a member of the group. Additionally, the database is updated to mark their membership as `ACTIVE`. 

#### Decline an invitation

When a user has a `PENDING` invitation to a group, they can decline the invitation by following these steps:

1. Go to the group page, which they will see in their UI since they have a pending invitation.
2. On the Overview, there will be a box that says, "Accept invitation?" with two buttons "Accept" and "Decline".
3. Click the "Decline" button.

After the user has declined the invitation, the row in the `members` table for the group and this user is deleted.

### Removing a user from a group

When an existing `OWNER` of a group wants to remove a user from the group, they take these steps:

1. Go to the group page.
2. Click the "Members" tab.
3. Find the user in the list and click the "Remove" button (likely under the three dot menu).
4. Click "Confirm" in the pop-up modal dialog.

This process deletes the row in the `members` table for the user. The current user cannot delete themselves from the group.

### Changing a member's role

When an existing `OWNER` of a group wants to change the role of a user in the group, they take these steps:

1. Go to the group page.
2. Click the "Members" tab.
3. Find the user in the list and click the "Change role" button (likely under the three dot menu).
4. Select the new role in the pop-up modal dialog.
5. Click "Confirm" in the pop-up modal dialog.

This process updates the row in the `members` table for the user and changes their role. The current user cannot change their own role.

### Leaving a group

An existing member of a group can leave the group as long as there is another member with the `OWNER` role. The user can leave the group by taking these steps:

1. Go to the group page.
2. Click the "Members" tab.
3. Find their user in the list and click the "Leave group" button (likely under the three dot menu).
4. Click "Confirm" in the pop-up modal dialog.

This process deletes the row in the `members` table for the current user and redirects to the dashboard of the app.

## Decisions so far

- **Production host:** Cloudflare Containers (the JVM app runs in a Docker image). Custom Domain on the fronting Worker handles DNS + automatic TLS. The Worker forwards HTTP to the container on port 8080.
- **Database:** Cloudflare D1 (managed SQLite, ≤ 10 GB / DB).
- **Access pattern:** the JVM calls D1's HTTP API directly (`api.cloudflare.com/.../d1/database/<id>/query`). No Worker on the data path.
- **Local dev:** `wrangler dev` runs a local D1 that exposes the same HTTP API shape as production. Single `D1Client` implementation; dev = prod.
- **Role modeling:** single `role` column with two values: `OWNER`, `CONTRIBUTOR`. No JSON arrays, no separate permission table.
- **Migrations runner:** `wrangler d1 migrations apply` (tracks applied migrations in the built-in `d1_migrations` table).

## Schema

```sql
-- groups: keyed by reverse-DNS name (no synthetic UUID; the name IS the identity)
CREATE TABLE groups (
  name              TEXT PRIMARY KEY,            -- 'org.lattejava'
  description       TEXT NOT NULL DEFAULT '',
  state             TEXT NOT NULL,               -- 'VERIFIED' | 'PENDING' | 'FAILED'
  verification_code TEXT NULL,                   -- '<random>' or NULL if verification is disabled
  created_at        INTEGER NOT NULL,            -- epoch millis
  verified_at       INTEGER
);

-- members: group x user, with role and invitation state
CREATE TABLE members (
  group_name       TEXT NOT NULL,               -- 'org.lattejava'
  user_id          TEXT NOT NULL,               -- FA user UUID
  role             TEXT NOT NULL,               -- 'OWNER' | 'CONTRIBUTOR'
  state            TEXT NOT NULL,               -- 'PENDING' | 'ACTIVE'
  invited_by       TEXT,                        -- FA UUID of the inviting OWNER; NULL for seeded rows
  invited_at       INTEGER,                     -- NULL for seeded rows
  joined_at        INTEGER,                     -- set when state -> 'ACTIVE'
  PRIMARY KEY (group_name, user_id),
  FOREIGN KEY (group_name) REFERENCES groups(name) ON DELETE CASCADE
);

CREATE INDEX members_user_id_idx ON members(user_id);

-- group_verifications: one outstanding DNS TXT challenge per group
CREATE TABLE group_verifications (
  group_name        TEXT PRIMARY KEY,            -- 'org.lattejava'
  started_at        INTEGER NOT NULL,
  last_checked_at   INTEGER,
  FOREIGN KEY (group_name) REFERENCES groups(name) ON DELETE CASCADE
);
```

### Schema notes

- **No synthetic group UUID.** The name is immutable and unique.
- **Members PK is `(group_name, user_id)`.** See workflow above for details on where the `user_id` is retrieved from FusionAuth.
- **No FK from `members.user_id` to FusionAuth.** FA is external; orphan rows are possible if a FA user is hard-deleted. Cleanup is a future concern.
- **No update tracking** This will be handled by an audit log that is outside the scope of this design.
- **No counts, error tracking, or any additional data requirements at this stage** All additional data will be handled in the future via an audit log or other means that are out of scope for this design.
- **Eventual consistency:** The application will not rely on the database to be consistent. Multiple verifications, deletions, inserts, or other operations should all be aware that the last operation wins.

## Implementation hints

Possible classes:

* GroupService: Handles all group-related operations including creation, deletion, and verification. This will use the DatabseClient.
* UserService: Handles all user-related operations including retrieval, creation, registration. This will leverage the FusionAuth APIs.
* MembershipService: Handles all membership-related operations, including inviting users and accepting or declining invitations. This will use the DatabaseClient and the FusionAuth APIs.
* DatabaseClient: Handles the HTTP calls to the database. This should take the model objects and convert them to SQL statements. It should also take the JSON responses and convert them to model objects. The public methods of this class should only work on model objects.
